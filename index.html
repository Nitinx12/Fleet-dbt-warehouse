    How dbt works here

    Four layers, each one run, then tested

    Each square is one table or model. dbt reads bronze through source(), builds layer by layer, and Airflow runs the tests before moving on. Nothing outside its layer writes to it.

    dbt run silver→dbt test→dbt run gold→dbt test→dbt run marts→dbt test→publish An error-severity failure stops the batch.
    Batch vs streaming

    Two planes that never mix

    The streaming layer runs beside the batch pipeline and only observes it.

    Production

    Daily batch

    • Source → bronze → dbt → marts → Databricks
    • Runs once a day, fully contracted and tested
    • Feeds BI dashboards and analysts
    Implemented

    Speed layer

    • Replay Mongo delivery events → Kafka delivery_events.v1 (+ DLQ)
    • PySpark validates, windows and tracks detention → Postgres realtime
    • reconcile_stream compares to gold and writes to audit.*; it never feeds silver, gold, marts or Databricks
    Quality & governance

    Fail fast, keep evidence, protect PII

    A failed contract or data test blocks the run. Only transient connection failures are retried.

    383dbt tests: 348 error, 35 warn severity
    104Python and Airflow test cases
    12contracts checked by make contracts-check
    9CI jobs plus full-history Gitleaks
    • Licence numbers are hashed in staging; the raw value stops there.
    • Dates of birth become age_band and never reach a mart.
    • Fuel card numbers are masked to the last four digits.
    • Incident descriptions stay in Postgres bronze, out of gold marts.
